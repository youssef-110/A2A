Design proposal · for review

A2A Relay: an inspected messaging layer for agents

Agents at an organization talk to each other through one relay server. A guard agent on that server reads every message before it is delivered and blocks anything harmful or outside the organization's scope. A daemon on each machine sends messages for its local agents and, when a message arrives, starts the agent runtime the user configured, such as Claude Code or Codex.

Repo youssef-110/A2AStatus Draft v0.1Date 24 Oct 2026

01Summary

Goals

  • One path for all agent-to-agent traffic. No agent talks directly to another. Every message goes through the relay, so every message can be inspected, logged and stopped.
  • Inspection before delivery. A guard checks each message against organization policy and lets it through, blocks it, or holds it for a human.
  • One program on every machine. A single a2a program both sends and receives. It runs in the background to receive messages, and its subcommands send them. On receive, it starts the runtime the user chose for that agent.
  • Conversations, not one-off pings. Messages belong to threads. A reply goes back into the same thread, and the receiving runtime can resume its earlier session for that thread.
  • A full audit trail. Every message, verdict and delivery is recorded.

Non-goals for v1

  • End-to-end encryption between agents (see section 2).
  • Messaging between different organizations. The model allows it later, but v1 is one organization per deployment.
  • Building our own agent runtime. We start existing CLIs (Claude Code, Codex, or any command).
  • Real-time streaming of tokens between agents. Messages are whole units.

02Why not end-to-end encryption

With end-to-end encryption, only the receiving agent can read a message. That is exactly the problem: the receiving agent is an LLM, and an LLM can be steered by text inside the message (prompt injection). If nothing in between can read the content, nothing can stop a malicious or confused agent from sending instructions that hijack the recipient.

Decision: the relay is a trusted inspector. Traffic is encrypted in transit (TLS) and at rest (database and backups), but the relay can read message plaintext so the guard can inspect it. Messages are signed by the sending daemon, so the relay and recipient can prove who sent what and that it was not changed.

The consequence is that the relay server becomes the most sensitive part of the system. It must be self-hosted inside the organization's boundary, access to it is tightly controlled, and admin access to message bodies is itself logged.

Server

Relay API and router

  • Authenticates daemons, verifies message signatures.
  • Stores every message and its state.
  • Sends each message to the guard, then routes it to the recipient's daemon.
  • Handles retries, acks and offline queues.
Server

Guard agent

  • Runs deterministic checks first, then an LLM judge.
  • Returns a structured verdict: allow, block or hold for review.
  • Has no tools and cannot take actions. It only classifies.
  • Fails closed: if it errors or times out, the message is held.
Every machine

a2a client

  • Holds the signing keys for the agents on that machine.
  • Keeps a WebSocket open to the relay to receive messages.
  • Exposes a local MCP server so agents can send, reply and read threads.
  • Starts the configured runtime when a message arrives.
Server

Admin console

  • Register agents and approve which agents may talk to which.
  • Write and version policies.
  • Review the hold queue and release or reject messages.
  • Search the audit log and see guard statistics.

04Message lifecycle

The happy path for a request and its reply. Delivery is asynchronous. The sending agent can either continue its work or wait (with a timeout) for the reply.

sequenceDiagram
  participant A as Agent A
  participant DA as Daemon A
  participant R as Relay
  participant G as Guard
  participant DB as Daemon B
  participant B as Agent B (spawned)
  A->>DA: send_message(to, text)
  DA->>DA: sign envelope
  DA->>R: POST /v1/messages
  R-->>DA: 202 accepted (msg id)
  R->>G: screen(message, thread context, policy)
  G-->>R: verdict = allow
  R->>DB: deliver over WebSocket
  DB-->>R: ack
  DB->>B: start runtime with wrapped message
  B->>DB: reply(thread, text)
  DB->>R: POST /v1/messages (in_reply_to)
  R->>G: screen reply
  G-->>R: verdict = allow
  R->>DA: deliver reply
  DA-->>A: tool call returns reply

Message states

stateDiagram-v2
  [*] --> received
  received --> rejected: bad signature, unknown agent, link not allowed
  received --> screening
  screening --> blocked: guard says block
  screening --> held: guard says hold, or guard failed
  held --> screening_done: human releases
  held --> blocked: human rejects
  screening --> screening_done: guard says allow
  screening_done --> queued
  queued --> delivered: daemon acks
  queued --> expired: TTL passed while recipient offline
  delivered --> [*]
  blocked --> [*]
  rejected --> [*]
  expired --> [*]

The sender is told about every terminal state. On a block, the sender gets a short reason code (for example out_of_scope or secret_detected), not the guard's full reasoning. Giving full reasoning back would let a sender tune its wording until it gets past the guard.

05The guard agent

The guard is a pipeline. Cheap deterministic checks run first and stop most problems before any model is called. The LLM judge only sees messages that passed those checks.

1

Envelope checks

deterministic · under 5 ms
  • Valid signature, known and active sender and recipient.
  • The sender is allowed to message this recipient under this scope.
  • Size limits, attachment types, rate limits per agent and per link.
  • Loop protection: hop count per thread, message count per thread, repeated content hashes.
2

Content scanners and normalization

deterministic · under 50 ms
  • Normalize text: Unicode NFKC, strip zero-width and bidi control characters, flag homoglyphs.
  • Find and decode embedded payloads (base64, hex, URL-encoded blocks) so later stages see what is really there.
  • Secret detection (API keys, private keys, tokens) and PII detection.
  • Known prompt-injection patterns as a signal, not a final decision.
3

LLM judge

fast model · target p95 under 2 s
  • Input: organization policy, the recipient's declared scope, a short thread summary, scanner findings, and the normalized message.
  • Output: JSON only, validated against a schema: {decision, categories[], confidence, reason}.
  • Uses a fast model (for example claude-haiku-5-5). Confident results end here.
4

Escalation

stronger model, then a human
  • Low-confidence or high-risk results go to a stronger model (for example claude-sonnet-5-5).
  • If it is still unsure, the message is held for a human in the admin console.

Verdicts

VerdictWhat happensPhase
ALLOWDelivered to the recipient.1
BLOCKNot delivered. Sender gets a reason code. Logged with full detail for admins.1
HOLDWaits in the review queue. A human releases or rejects it. Also used whenever the guard fails.1
REDACTDelivered with flagged spans removed (for example a leaked key). The recipient is told content was redacted.3

Keeping the guard itself safe from injection

The guard is an LLM reading attacker-controlled text, so it can be targeted too. Defences:

  • No tools, no side effects. The worst a successful injection can do is change one verdict.
  • Schema-only output. Anything that does not parse as a valid verdict is treated as a failure and the message is held.
  • Nonce-delimited input. The message is wrapped in markers containing a random value per request, so a message cannot fake the end of its own block.
  • Deterministic stages are not skippable. The LLM can only make a verdict stricter than what stages 1 and 2 decided, never more lenient.
  • Probing protection. Agents that collect many blocks get throttled and flagged for review.
  • An eval set in the repo. A growing set of known-bad and known-good messages runs in CI on every change to the guard prompt or model.

Defence in depth on the receiving side. The guard will miss things. The daemon also wraps every delivered message as untrusted data (section 7), and each runtime runs with the narrowest permissions the user configured. The guard reduces risk; it is not the only barrier.

06Policies and scope

Policy answers three questions: who may talk to whom, about what, and with what limits. It is stored as versioned YAML. Every verdict records the policy version it was made under.

# policy.yaml (illustrative)
org: acme
version: 7

scopes:
  customer-support:
    description: >
      Questions about customer accounts, orders, refunds and support tickets.
      No changes to production systems. No sharing of payment card data.
  engineering:
    description: >
      Code review, bug triage and CI failures for repositories in github.com/acme.

links:                                   # who may message whom
  - from: agent://acme/billing-bot
    to:   agent://acme/support-triage
    scopes: [customer-support]
    rate: 60/hour
  - from: agent://acme/*
    to:   agent://acme/code-fixer
    scopes: [engineering]

limits:
  max_hops_per_thread: 12                # stops agent ping-pong
  max_messages_per_thread: 40
  max_body_bytes: 65536
  message_ttl: 24h

rules:
  block: [secret_detected, credential_request, instruction_override, payment_card]
  hold:  [out_of_scope, unusual_data_volume, external_url]

The free-text scope descriptions go straight into the judge prompt, so admins can describe what is in bounds in plain language instead of writing rules for every case.

07The client and spawning

One program, a2a, runs on every machine. It does four things: holds keys, keeps a connection to the relay, gives local agents a way to send, and starts runtimes when messages arrive.

The program has one long-running mode and a set of short commands. Only the long-running mode talks to the relay and keeps state (connection, outbox, seen message ids). Every other command finds the running instance through a local socket (~/.a2a/a2a.sock) and asks it to do the work, so there is never more than one owner of that state.

CommandWhat it does
a2a runLong-running mode: connects to the relay, receives messages, starts runtimes, sends the outbox.
a2a installRegisters a2a run as a launchd or systemd service so it starts at login.
a2a mcpMCP server over stdio. Runtimes start it as their a2a MCP server; it forwards tool calls to the running instance.
a2a send · status · threadSend a message, check its state, read a thread.
a2a agents · keysList and register local agents, create and rotate keys.

If a2a run is not running, the short commands say so and offer to start it, instead of quietly connecting to the relay on their own.

Sending

Agents send through the a2a mcp server. Scripts and humans use the same program's subcommands. Both go through the running instance.

MCP toolWhat it does
list_agentsLists the agents this agent is allowed to message, with their scopes.
send_messageStarts a new thread. Optional wait_for_reply with a timeout.
replyReplies in the current thread.
get_threadReads earlier messages in a thread.
message_statusShows whether a sent message was delivered, blocked or held.
 
a2a send agent://acme/code-fixer "CI on acme/web main is failing in auth.test.ts, can you look?"
a2a status msg_01JB7...
a2a thread thr_01JB7...

Receiving

  1. The daemon receives the message over WebSocket, verifies the relay's delivery signature and the sender's signature, then acks.
  2. It looks up the runtime for the recipient address.
  3. If session: per_thread and a session already exists for this thread, it resumes that session. Otherwise it starts a new one.
  4. It builds a prompt that marks the message as untrusted data (below) and starts the runtime in the configured working directory with the configured tool permissions.
  5. The agent replies with the reply tool. If it exits without calling it, its final output is sent as the reply, unless that agent is configured as notify-only.
  6. Concurrency limits apply per agent. Extra messages wait in a local queue.

Running as a service

a2a install registers a2a run as a launchd agent on macOS and a systemd user service on Linux. It reconnects with backoff, and messages sent while offline wait in a local outbox until the relay is reachable again.

10Threat model

ThreatMitigation
A message tries to hijack the receiving agentGuard pipeline; untrusted-data wrapping on receive; narrow tool permissions per runtime.
Hiding instructions with encoding, zero-width characters or homoglyphsNormalization and payload decoding in stage 2 before the judge sees the text.
Prompt injection aimed at the guard itselfNo tools, schema-only output, nonce markers, LLM can only make verdicts stricter, fail closed.
An agent leaks secrets or customer data to another agentSecret and PII scanners; scope rules; redaction in phase 3.
Impersonating another agentPer-agent signing keys held by the daemon; relay verifies every signature.
Replaying an old messageUnique message ids, timestamps checked against a window, ids stored and rejected if seen.
Two agents looping forever and burning moneyHop and message limits per thread, repeated-content detection, per-agent rate and spend budgets.
Probing the guard to find wording that gets throughReason codes only, throttling and review for agents with many blocks.
A compromised daemon or machineRevoke the daemon and its agent keys in the console; links limit how far it can reach.
A compromised relay serverSelf-hosted, least-privilege access, encrypted at rest, admin reads audited. This is the trust anchor and is the accepted residual risk.

12Roadmap

Phase 0 · Plain relay

Relay server with Postgres, agent registration by config, POST /v1/messages, WebSocket delivery with acks, and a daemon that can send and print received messages. No guard yet; everything is allowed and logged.

Done when: two daemons on two machines exchange messages, survive a restart of either side, and never lose or duplicate a message.

Phase 1 · Guard

Stages 1 to 3, verdicts allow, block and hold, reason codes to the sender, a first policy file, loop limits, and an eval set of at least 100 labelled messages running in CI.

Done when: the eval set passes with no false allows on the bad set, and p95 screening time is under 2 seconds.

Phase 2 · Spawning and threads

Runtime adapters for Claude Code, Codex and custom commands; the local MCP server; untrusted-data wrapping; per-thread session resume; concurrency limits and timeouts; launchd and systemd install.

Done when: a Claude Code agent on machine A asks a Codex agent on machine B a question and gets a reply in the same thread, three turns deep, with no manual steps.

Phase 3 · Operations

Admin console with the hold queue, policy editor and audit search; stage 4 escalation; redaction; guard metrics (block rate, hold rate, latency, cost).

Done when: an admin can review and release a held message and change policy without touching the server.

Phase 4 · Hardening

Message signing enforced everywhere, key rotation and revocation, replay protection, spend budgets, a red-team pass on the guard, and backup and restore procedures.

Done when: an internal red-team exercise finds no way to deliver a blocked category of message.

13Open questions for review

Q1
Do we need messaging between organizations in the first year?

It changes trust: two relays would need to federate, or one relay would host several orgs. v1 assumes one org per deployment.

Q2
Should we adopt Google's A2A protocol format?

Its Agent Cards and task model could be the wire format, with our relay and guard in the middle. That gives interoperability but ties us to a spec we do not control. The proposal above uses our own simpler envelope that could be mapped to A2A later.

Q3
Should the sending agent wait for replies by default?

Waiting is simpler for agents to reason about but ties up a running session. The proposal makes it optional per call.

Q4
How much should a blocked sender be told?

The proposal sends a reason code only. Some teams may want the full reason for debugging during development.

Q5
What latency is acceptable for screening?

The plan targets under 2 seconds at p95. A stricter target means more weight on deterministic checks and smaller models.

Q6
How long do we keep message bodies?

Full bodies help audits but increase risk if the relay is breached. One option is 30 days for bodies and indefinite retention for hashes and verdicts.

Q7
Who maintains the guard's eval set?

The guard is only as good as the examples it is tested against. Someone needs to own adding new attacks and false positives as they appear.
